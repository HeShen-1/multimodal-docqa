## 架构演进规划

### 当前架构（v1.0）

```
架构特点：
- 单体应用，所有功能在一个进程中
- 同步处理，请求阻塞等待
- 简单部署，适合快速开发

存在问题：
- 文档处理阻塞API响应
- 无法水平扩展
- 单点故障风险
```

### 目标架构（v2.0）

```
架构演进方向：
1. 服务分层
   - API层：处理HTTP请求
   - 业务层：核心业务逻辑
   - 数据层：数据持久化
   - 任务层：异步任务处理

2. 异步化改造
   - 文档处理异步化（Celery）
   - 长时间查询异步化
   - WebSocket实时推送

3. 缓存架构
   - L1缓存：本地内存（LRU）
   - L2缓存：Redis（分布式）
   - L3缓存：数据库

4. 高可用设计
   - 服务多实例部署
   - 负载均衡（Nginx）
   - 数据库主从复制
   - Redis哨兵模式
```

## 功能模块设计

### Phase 1: 用户认证服务

**模块职责**: 提供用户注册、登录、权限管理功能

**核心组件**:

1. **AuthService（认证服务）**
   ```
   职责：
   - 用户注册和登录验证
   - Token生成和验证
   - 密码加密和校验
   
   关键方法：
   - register(username, email, password): 用户注册
   - login(username, password): 用户登录
   - verify_token(token): 验证Token有效性
   - refresh_token(refresh_token): 刷新访问令牌
   
   依赖：
   - passlib: 密码加密
   - python-jose: JWT Token生成
   - Redis: Token黑名单存储
   ```

2. **PermissionService（权限服务）**
   ```
   职责：
   - 基于角色的访问控制（RBAC）
   - 资源权限验证
   - 权限装饰器
   
   权限模型：
   - Role（角色）: admin, user
   - Permission（权限）: read, write, delete
   - Resource（资源）: document, query, conversation
   
   实现方式：
   - 使用装饰器检查权限
   - 支持动态权限配置
   - 权限缓存提升性能
   ```

3. **RateLimiter（限流器）**
   ```
   职责：
   - API访问频率限制
   - 防止恶意攻击
   - 保护系统资源
   
   限流策略：
   - 固定窗口：每分钟N次
   - 滑动窗口：更精确的限流
   - 令牌桶：支持突发流量
   
   限流级别：
   - IP级别：防止单IP攻击
   - 用户级别：公平使用资源
   - 接口级别：不同接口不同限制
   ```

**数据库设计**:
```
users表：
- 主键：id (UUID)
- 索引：username, email
- 字段：password_hash, role, is_active
- 关系：一对多（documents, conversations）

token_blacklist表：
- 主键：id (UUID)
- 索引：token, expires_at
- 用途：存储已失效的Token
- 清理：定时任务清理过期记录
```

**实现步骤**:
1. 安装依赖：python-jose, passlib, slowapi
2. 创建数据库表和模型
3. 实现AuthService核心方法
4. 添加认证中间件
5. 配置限流规则
6. 编写单元测试

### Phase 3: 缓存优化系统

**模块职责**: 提升系统性能，减少数据库压力

**缓存架构**:

1. **多级缓存设计**
   ```
   L1缓存（本地内存）：
   - 工具：functools.lru_cache
   - 容量：1000条
   - 用途：热点数据、配置信息
   - 优点：访问速度最快
   - 缺点：不共享，容量有限
   
   L2缓存（Redis）：
   - 工具：redis-py
   - 容量：根据内存配置
   - 用途：查询结果、向量检索结果
   - 优点：分布式共享
   - 缺点：网络开销
   
   L3缓存（数据库）：
   - 工具：PostgreSQL
   - 容量：磁盘空间
   - 用途：持久化数据
   - 优点：可靠性高
   - 缺点：访问速度慢
   ```

2. **缓存策略**
   ```
   缓存更新策略：
   - Cache Aside：先查缓存，未命中查数据库
   - Write Through：写入时同时更新缓存
   - Write Behind：异步更新缓存
   
   缓存失效策略：
   - TTL过期：设置合理的过期时间
   - 主动失效：数据更新时删除缓存
   - LRU淘汰：内存不足时淘汰最少使用
   
   缓存预热：
   - 系统启动时加载热点数据
   - 定时任务更新缓存
   - 用户访问时按需加载
   ```

3. **缓存装饰器**
   ```
   实现思路：
   - 使用Python装饰器封装缓存逻辑
   - 支持自定义缓存键生成
   - 支持设置过期时间
   - 支持缓存穿透保护
   
   使用示例：
   @cache_result(expire=1800, prefix="query")
   async def query_with_cache(question, doc_ids):
       # 查询逻辑
       pass
   
   装饰器功能：
   - 自动生成缓存键
   - 检查缓存是否存在
   - 缓存未命中时执行函数
   - 将结果存入缓存
   ```

**实现步骤**:
1. 设计缓存键命名规范
2. 实现缓存装饰器
3. 为关键接口添加缓存
4. 实现缓存管理接口
5. 监控缓存命中率
6. 优化缓存策略

### Phase 5: 智能分析服务

**模块职责**: 提供文档分析和洞察功能

**核心组件**:

1. **SummaryService（摘要服务）**
   ```
   摘要生成方法：
   
   抽取式摘要：
   - 使用TextRank算法
   - 提取关键句子
   - 保持原文表述
   - 适合快速预览
   
   生成式摘要：
   - 使用LLM重新表述
   - 更加简洁流畅
   - 可控制风格
   - 适合深度理解
   
   混合式摘要：
   - 先抽取关键内容
   - 再用LLM润色
   - 兼顾速度和质量
   
   实现流程：
   1. 分析文档结构
   2. 提取关键段落
   3. 生成摘要文本
   4. 质量评估和优化
   ```

2. **KeywordService（关键词服务）**
   ```
   提取方法：
   
   TF-IDF方法：
   - 统计词频和逆文档频率
   - 计算TF-IDF分数
   - 选择Top K关键词
   - 优点：快速、稳定
   
   TextRank方法：
   - 构建词语关系图
   - 使用PageRank算法
   - 考虑词语共现关系
   - 优点：考虑语义关系
   
   LLM提取方法：
   - 使用Prompt引导LLM
   - 理解语义和上下文
   - 提取主题关键词
   - 优点：准确度高
   
   实现流程：
   1. 文本预处理（分词、去停用词）
   2. 应用提取算法
   3. 合并多种方法结果
   4. 按权重排序返回
   ```

3. **CompareService（对比服务）**
   ```
   对比维度：
   
   内容相似度：
   - 计算文档向量相似度
   - 使用余弦相似度
   - 返回0-1之间的分数
   
   主题分析：
   - 提取两个文档的主题
   - 找出共同主题
   - 识别独特主题
   
   结构对比：
   - 分析文档结构
   - 对比章节组织
   - 识别结构差异
   
   实现流程：
   1. 分别分析两个文档
   2. 计算各维度指标
   3. 生成对比报告
   4. 可视化展示结果
   ```

### Phase 7: 系统稳定性增强

**模块职责**: 提升系统可靠性和容错能力

**核心组件**:

1. **CircuitBreaker（熔断器）**
   ```
   职责：
   - 防止级联故障
   - 快速失败保护
   - 自动恢复检测
   
   状态机设计：
   - Closed（关闭）: 正常状态，请求正常通过
   - Open（打开）: 熔断状态，直接返回错误
   - Half-Open（半开）: 尝试恢复，允许部分请求
   
   状态转换条件：
   - Closed → Open:
     * 错误率 > 50%
     * 连续失败次数 > 5次
     * 响应超时 > 10秒
   - Open → Half-Open:
     * 等待60秒后尝试恢复
   - Half-Open → Closed:
     * 连续成功3次
   - Half-Open → Open:
     * 任意一次失败
   
   实现方案：
   - 使用pybreaker库
   - 为外部服务调用添加熔断
   - 配置熔断参数
   - 监控熔断事件
   
   应用场景：
   - Ollama服务调用
   - 向量数据库查询
   - 外部API调用
   ```

2. **GracefulDegradation（优雅降级）**
   ```
   职责：
   - 在系统压力大时降级非核心功能
   - 保证核心服务可用
   - 自动恢复正常服务
   
   降级级别：
   - L0（正常）: 所有功能正常
   - L1（轻度降级）:
     * 关闭相似问题推荐
     * 关闭文档推荐
     * 减少检索结果数量
   - L2（中度降级）:
     * 关闭Thinking Chain
     * 关闭Rerank重排序
     * 简化响应内容
   - L3（重度降级）:
     * 限制并发查询数
     * 限制文档上传
     * 只保留基础查询
   
   触发条件：
   - CPU使用率 > 80%（L1）
   - CPU使用率 > 90%（L2）
   - 内存使用率 > 90%（L2）
   - 任务队列积压 > 100（L2）
   - 数据库连接池耗尽（L3）
   
   实现方案：
   - 使用配置中心动态控制
   - 实现降级开关
   - 监控系统资源
   - 自动触发降级
   - 定期检测恢复条件
   ```

3. **RetryMechanism（重试机制）**
   ```
   职责：
   - 自动重试失败请求
   - 提高请求成功率
   - 避免瞬时故障影响
   
   重试策略：
   - 固定延迟: 每次等待固定时间
   - 指数退避: 1s、2s、4s、8s
   - 随机退避: 避免惊群效应
   
   重试配置：
   - 最大重试次数: 3次
   - 初始延迟: 1秒
   - 最大延迟: 30秒
   - 超时时间: 60秒
   
   幂等性保证：
   - 使用请求ID去重
   - 检查操作是否已执行
   - 避免重复操作副作用
   
   实现方案：
   - 使用tenacity库
   - 配置重试装饰器
   - 记录重试日志
   - 监控重试率
   
   适用场景：
   - 网络请求
   - 数据库操作
   - 外部服务调用
   - 文件操作
   ```

4. **FallbackStrategy（备用策略）**
   ```
   职责：
   - 主服务不可用时切换到备用方案
   - 保证服务连续性
   - 自动检测主服务恢复
   
   备用模型配置：
   - 主模型: qwen3-vl:2b-thinking
   - 备用模型1: qwen2:7b
   - 备用模型2: llama3:8b
   
   切换条件：
   - 主模型连续失败3次
   - 主模型响应超时（> 30s）
   - 主模型服务不可用
   
   恢复检测：
   - 每5分钟检测主模型状态
   - 使用健康检查接口
   - 成功后自动切回主模型
   
   实现方案：
   - 配置多个Ollama实例
   - 实现模型路由器
   - 记录切换日志
   - 监控模型可用性
   
   其他备用策略：
   - 向量数据库: ChromaDB ↔ Milvus
   - 缓存: Redis ↔ 本地缓存
   - 存储: 本地 ↔ 对象存储
   ```

5. **HealthCheck（健康检查）**
   ```
   职责：
   - 定期检查服务健康状态
   - 及时发现故障
   - 触发自动恢复
   
   检查项目：
   - 数据库连接
   - Redis连接
   - Ollama服务
   - 向量数据库
   - 磁盘空间
   - 内存使用
   
   检查频率：
   - 关键服务: 每30秒
   - 一般服务: 每5分钟
   - 资源检查: 每1分钟
   
   健康状态：
   - Healthy: 所有检查通过
   - Degraded: 部分检查失败
   - Unhealthy: 关键检查失败
   
   实现方案：
   - 实现/health端点
   - 返回详细健康信息
   - 集成到负载均衡器
   - 配置自动重启
   ```

**实现步骤**:
1. 安装依赖（pybreaker, tenacity）
2. 实现熔断器和重试机制
3. 配置降级策略
4. 实现备用模型切换
5. 添加健康检查端点
